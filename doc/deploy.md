# Deploy

A push to `main` deploys the `dev` stage: Cloudflare Workers Builds runs `npm run deploy` on the Worker `tumpel-control-plane-dev`, which applies the infra, migrates D1, deploys the Worker and sets its secrets. The trigger is declared in `cloudflare-builds-bootstrap` (`infra/projects.auto.tfvars.json`, project `tumpel`) with the build variables `NODE_VERSION`, `TUMPEL_STAGE` and `TUMPEL_ACCOUNT_ID`. The deploy needs Node and OpenTofu (it downloads a checksummed binary) but not cargo, so the build installs the npm workspaces only. After every deploy of a stage, `npm run proof:e2e` runs the sixteen-step proof of EDD-006 against that stage (`doc/EDD/006-end-to-end-proof.md`), on the host that `TUMPEL_PROOF_HOST` names. Do not deploy from a checkout; the commands below are for bootstrapping an account or a new stage.

The control plane deploys per stage; the stage is `TUMPEL_STAGE` and defaults to `dev`. Every stage serves under the zone `tumpel.dev`, declared in `packages/control-plane/infra/domains.tf`. The control plane Worker answers on the custom domain `api.<stage>.tumpel.dev` (API, MCP, browser pages and releases). It also serves the issuer on the custom domain `id.<stage>.tumpel.dev`. The Worker `tumpel-dashboard-<stage>` serves the dashboard (`packages/dashboard`, static assets behind a Worker) on the custom domain `<stage>.tumpel.dev`, and it answers `app.<stage>.tumpel.dev` with a 308 to the dashboard. Stage `prod` drops the stage label: `api.tumpel.dev`, `id.tumpel.dev`, and the dashboard on the apex `tumpel.dev`. The issuer name never moves once tenants pin it, so its custom domain refuses to be destroyed. Stage `dev` serves the API on `api.dev.tumpel.dev` and its dashboard on `dev.tumpel.dev`. The dev GitHub App is https://github.com/apps/tumpel-dev, owned by the organization https://github.com/tumpel. Zone resources go through the provider alias `bootstrap`, because `tumpel-tofu` holds no zone permission. Each custom domain brings its own certificate; the zone certificate covers one label under `tumpel.dev` only, so a proxied record at `<name>.<stage>.tumpel.dev` serves no TLS. A custom domain needs the Worker to exist, so the first deploy of a stage applies the infra without it, deploys the Worker, and applies again. Neither Worker serves a workers.dev host (`workers_dev` is false in both `wrangler.jsonc` files).

A stage is a wrangler environment of the same name in `packages/control-plane/wrangler.jsonc`, plus one OpenTofu state, `tumpel-<stage>.tfstate` in `tumpel-tfstate`. Each environment repeats the bindings, vars and Durable Object migrations, because wrangler does not inherit them. Account-wide resources carry the stage in their names: `tumpel-control-plane-<stage>`, `tumpel-sessions-<stage>`, `tumpel browser pages <stage>` and its policy. The D1 database is named `tumpel-<stage>` when a stage creates it; `dev` adopted the original database, still named `tumpel`, and OpenTofu ignores later name changes. To add a stage, add its `env` block, run `TUMPEL_STAGE=<stage> npm run deploy:infra`, copy the printed `database_id` into that block, and deploy.

The account token is `tumpel-tofu`. It carries Access: Apps and Policies Write, Access: Policies Write, Access: Organizations, Identity Providers, and Groups Read, Account Settings Read, D1 Write, Workers Scripts Write and Workers R2 Storage Write. To add a permission group, PUT the token by id with the group appended, using the token-minting key; the token value stays the same. OpenTofu keeps its state in the R2 bucket `tumpel-tfstate`, reached with the `tumpel-tfstate` token as S3 keys. Both are stored in dotfiles as `tumpel-tofu-token` and `tumpel-tfstate-s3`. `~/.config/tumpel/cf-env` (mode 600) holds `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `TFSTATE_ACCESS_KEY_ID`, `TFSTATE_SECRET_ACCESS_KEY` and `TUMPEL_APPROVER_EMAILS` (a JSON list).

The build reads its secrets from the private R2 bucket `tumpel-builder-secrets`, written once by `tofu-bootstrap tumpel --secrets <file> --debug-token-exists` with the token Builds injects: `CLOUDFLARE_TOFU_TOKEN`, both `TFSTATE_*` keys and `deploy.secrets.json` (the token-minting key `TUMPEL_BOOTSTRAP_API_TOKEN`, and `TUMPEL_APPROVER_EMAILS`). The Builds variables API refuses account-owned tokens, so these live as bucket objects. A deploy takes the bootstrap key from the `TUMPEL_BOOTSTRAP_API_TOKEN` variable when set. Otherwise it reads `deploy.secrets.json` on Workers Builds and dotfiles everywhere else.

Bootstrap order on a new account:

1. Mint `tumpel-tofu` and `tumpel-tfstate` with the token-minting key, create `tumpel-tfstate`, and write `cf-env`.
2. `npm run deploy:infra` applies `packages/control-plane/infra/`: the D1 database `tumpel`, the R2 bucket `tumpel-sessions-<stage>` (transcript chunks and snapshots), and the Access application `tumpel browser pages <stage>`, which puts `/device`, `/v1/tenants`, `/v1/device/approve`, `/v1/device/deny`, `/oauth/consent`, `/invitations/accept`, `/v1/invitations/accept` and the three `/github/app/` pages behind the one-time PIN. It also puts `/v1/issuer-keys/rotate` behind Access, which lets only the proof service token through there.
3. Copy the `database_id` it prints into the stage's `env` block of `wrangler.jsonc` and commit.
4. Presigned snapshot URLs need an R2 API token with Object Read & Write on `tumpel-sessions-<stage>` only. OpenTofu manages it as `tumpel-r2-<stage>` in `infra/tokens.tf`. The `bootstrap` provider alias mints it with the account's token-minting key `reader-cloudflare-tofu-token`. Cloudflare refuses Account API Tokens Write on a token that another token minted, so `tumpel-tofu` cannot hold that permission. `npm run deploy` decrypts the key in process from dotfiles and passes it as `TF_VAR_bootstrap_api_token`. The output `worker_secrets` derives the S3 key pair from the token (access key id is the token id, secret is the SHA-256 hex of the token value) and `npm run deploy` puts `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` on the Worker after deploying it. The Worker signs short-lived snapshot upload and download URLs with it; hosts never hold a storage key.
5. After the first deploy, open `/github/app/setup` on the stage in a browser and register the stage's GitHub App. Every self-hosted control plane registers its own App, one per stage. Add `?organization=<login>` to register it under an organization. GitHub returns to `/github/app/created`, and the page refuses once an App exists.

The Worker reads its turn budgets, snapshot delay and deadline, dispatch grant lifetime and transcript chunk size from the `TUMPEL_SETTINGS` var in `wrangler.jsonc`, checked against `ControlPlaneSettings` in `packages/api/models.tsp`.

Commands, for bootstrap only:

- `npm run deploy` applies the stage's infra and refuses a plan that destroys anything but the retired `app` record and route and the retired `id` record. It builds the dashboard against `https://api.<stage>.tumpel.dev` and deploys it as `tumpel-dashboard-<stage>` without the Workers Builds name override. It then applies D1 migrations, deploys the control plane Worker with `ACCESS_ISSUER`, `ACCESS_AUD` and `ISSUER_HOSTNAME` from the tofu outputs, and sets the R2 Worker secrets. The control plane deploys last, so a failed dashboard deploy never replaces the API. A first deploy of either Worker applies the infra without its custom domain, and applies again once the Worker exists.
- `npm run deploy:migrate` applies D1 migrations only.
- `npm run proof:e2e` validates a stage after its deploy: it runs the sixteen steps of EDD-006 against the stage's Worker and the host `TUMPEL_PROOF_HOST` (default `tumpel-host`), and loads the subscription token and its expiry in process from the host Claude Code credential `~/.claude/.credentials.json` (`TUMPEL_PROOF_CREDENTIAL` unset or `claude-credentials[:<path>]`), or from `TUMPEL_PROOF_CREDENTIAL=dotfiles:<key name>` together with `TUMPEL_PROOF_CREDENTIAL_EXPIRES_AT=<ISO 8601 date-time with offset>`.
- `npm run proof -- <command>` runs a command with `TUMPEL_PROOF_CLIENT_ID` and `TUMPEL_PROOF_CLIENT_SECRET` read from the stage's tofu outputs. It prints neither value. A command named `tumpel` runs the release CLI.
- `npm run proof`, `npm run proof:e2e` and `npm run issuer:rotate` download the current release's CLI for this machine and its Amd64 supervisor into `.tmp/proof-release/`, and check each against the sha256 that `current.json` names. `TUMPEL_PROOF_CLI` and `TUMPEL_PROOF_SUPERVISOR` replace them with local builds (`npm run cli:build`, `npm run supervisor:build`).

Sign a terminal in with `tumpel login --endpoint https://api.dev.tumpel.dev`.

Connect claude.ai in Settings, Connectors, Add custom connector. Enter the stage's origin followed by `/mcp`, and leave the client id and secret empty. Choose Connect and sign in through Access, with an email that is an approver and owns a tenant.

The end-to-end proof signs in without a person: `infra/proof.tf` mints the Access service token `tumpel-proof-<stage>` with the `bootstrap` alias and lets it through the Access application with a `non_identity` policy. `npm run deploy` sets its client id as the Worker var `ACCESS_PROOF_COMMON_NAME`. The Worker accepts that service token on `/v1/device/approve`, `/oauth/consent` and `/v1/device/deny` only, as the owner of the tenant `Tumpel proof`. That tenant's id and principal id derive from the client id, and the Worker creates both on first use. `npm run proof -- tumpel login --endpoint <stage url>` approves its own code with it.

## Releases

`.github/workflows/release.yml` runs on a push to `main` that changes the supervisor, the guest or the release code. It runs on the runner that the repository variable `BUILD_RUNNER` names, and on `ubuntu-24.04` when the variable is unset (`doc/test-host.md`). The workflow builds the supervisor, the `tumpel` CLI (`npm run cli:build`) and the guest images for amd64 and arm64. It publishes them to the R2 bucket `tumpel-releases-<stage>`, which is `dev` unless a manual run names another stage.

Every object in the bucket is stored once under its digest and never changes:

- `supervisor/<arch>/<sha256>` holds a supervisor binary.
- `cli/<arch>/<sha256>` holds a CLI binary.
- `images/<harness>/<version>/<arch>/<digest>` holds an ext4 image or its manifest.
- `kernels/<arch>/<sha256>` holds a kernel.

The one object that changes is `current.json`, the current release as a `ReleaseManifest` (`packages/api/release.tsp`). It holds `releaseVersion`, `commit`, `channelProtocolVersion`, `supervisors` and `clis` (each `architecture`, `sha256`, `sizeBytes`) and `images` (`harness`, `harnessVersion`, `architecture`, `imageDigest`, `kernelDigest`, `manifestDigest`, `ociDigest`). The control plane refuses a manifest whose `channelProtocolVersion` differs from the channel protocol.

The control plane serves `GET /v1/releases/current` without sign-in. `GET /v1/releases/supervisor/{architecture}` and `GET /v1/releases/cli/{architecture}` answer 302 to a presigned URL that lives 5 minutes, so a fresh host needs only `curl -fL <origin>/v1/releases/supervisor/Amd64`. Hosts on `dev` boot only images that a published release carries. A turn whose release lacks the session's image fails ImageNotReleased. `tumpel harness pin` refuses a version that the release carries for none of the tenant's host architectures.

The token `tumpel-releases-upload-<stage>` writes the bucket. `npm run release:secrets` sets the workflow's secrets `CLOUDFLARE_ACCOUNT_ID`, `R2_RELEASES_SECRET_ACCESS_KEY` and `R2_RELEASES_ACCESS_KEY_ID` from the tofu outputs. It prints none of them.

## Issuer

The issuer is the control plane Worker on `id.<stage>.tumpel.dev`, which the Worker var `ISSUER_HOSTNAME` names. There it serves `/.well-known/openid-configuration` and `/.well-known/jwks.json`, and it answers 404 to every other path. The Worker generates each RS256 key itself, at 2048 bits. A key's `kid` is its RFC 7638 thumbprint. The central table `issuer_keys` holds each private key, sealed under a data key that `SECRETS_KEK` wraps, and its `signs_from` time. A token lives 300 s and carries `iss`, `sub`, `aud`, `iat`, `nbf`, `exp` and `jti`. Its `sub` is `tenant:<tenantId>:persona:<name>:job:prebuild`.

`npm run issuer:rotate` rotates the key through `/v1/issuer-keys/rotate`. A rotation publishes the new key 24 h before it starts signing. The old key stays published for 24 h after its successor starts signing. The rotation answers `{signingKid, kid, signsFrom}`. A rotation while a key is still waiting to sign returns that key and adds none, so prod holds three keys or fewer. A person signed in through Access gets 403 `Only the operator tooling rotates`.
