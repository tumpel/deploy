# Deploy

A push to `main` deploys the `dev` stage: Cloudflare Workers Builds runs `npm run deploy` on the Worker `tumpel-control-plane-dev`, which applies the infra, migrates D1, deploys the Worker and sets its secrets. The trigger is declared in `cloudflare-builds-bootstrap` (`infra/projects.auto.tfvars.json`, project `tumpel`) with the build variables `NODE_VERSION`, `TUMPEL_STAGE` and `TUMPEL_ACCOUNT_ID`. The deploy needs Node and OpenTofu (it downloads a checksummed binary) but not cargo, so the build installs the npm workspaces only. After every deploy of a stage, `npm run proof:e2e` runs the twelve-step proof of EDD-006 against that stage (`doc/EDD/006-end-to-end-proof.md`), on the host that `TUMPEL_PROOF_HOST` names. Do not deploy from a checkout; the commands below are for bootstrapping an account or a new stage.

The control plane deploys per stage; the stage is `TUMPEL_STAGE` and defaults to `dev`. The `dev` stage runs at https://tumpel-control-plane-dev.matthijs-f49.workers.dev.

A stage is a wrangler environment of the same name in `packages/control-plane/wrangler.jsonc`, which repeats the bindings, vars and Durable Object migrations because wrangler does not inherit them, and one OpenTofu state, `tumpel-<stage>.tfstate` in `tumpel-tfstate`. Account-wide resources carry the stage: the Worker `tumpel-control-plane-<stage>`, the R2 bucket `tumpel-sessions-<stage>`, the Access application `tumpel browser pages <stage>` and its policy. The D1 database is named `tumpel-<stage>` when a stage creates it; `dev` adopted the original database, still named `tumpel`, and OpenTofu ignores later name changes. To add a stage, add its `env` block, run `TUMPEL_STAGE=<stage> npm run deploy:infra`, copy the printed `database_id` into that block, and deploy.

The account token is `tumpel-tofu`. It carries Access: Apps and Policies Write, Access: Policies Write, Access: Organizations, Identity Providers, and Groups Read, Account Settings Read, D1 Write, Workers Scripts Write and Workers R2 Storage Write. To add a permission group, PUT the token by id with the group appended, using the account's token-minting key; the token value stays the same. OpenTofu keeps its state in the R2 bucket `tumpel-tfstate`, reached with the `tumpel-tfstate` token as S3 keys. Both are stored in dotfiles as `tumpel-tofu-token` and `tumpel-tfstate-s3`. `~/.config/tumpel/cf-env` (mode 600) holds `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `TFSTATE_ACCESS_KEY_ID`, `TFSTATE_SECRET_ACCESS_KEY` and `TUMPEL_APPROVER_EMAILS` (a JSON list).

The build reads its secrets from the private R2 bucket `tumpel-builder-secrets`, written once by `tofu-bootstrap tumpel --secrets <file> --debug-token-exists` with the token Builds injects: `CLOUDFLARE_TOFU_TOKEN`, `TFSTATE_ACCESS_KEY_ID`, `TFSTATE_SECRET_ACCESS_KEY` and `deploy.secrets.json` (`TUMPEL_BOOTSTRAP_API_TOKEN`, the token-minting key, and `TUMPEL_APPROVER_EMAILS`). The Builds variables API refuses account-owned tokens, so these are bucket objects rather than build secrets. `deploy` takes the bootstrap key from the `TUMPEL_BOOTSTRAP_API_TOKEN` variable when set, from `deploy.secrets.json` on Workers Builds, and from dotfiles otherwise.

Bootstrap order on a new account:

1. Mint `tumpel-tofu` and `tumpel-tfstate` from the account's token-minting key, create `tumpel-tfstate`, and write `cf-env`.
2. `npm run deploy:infra` applies `packages/control-plane/infra/`: the D1 database `tumpel`, the R2 bucket `tumpel-sessions-<stage>` (transcript chunks and snapshots), and the Access application `tumpel browser pages <stage>`, which puts `/device`, `/v1/tenants`, `/v1/device/approve`, `/v1/device/deny` and `/oauth/consent` behind the one-time PIN.
3. Copy the `database_id` it prints into the stage's `env` block of `packages/control-plane/wrangler.jsonc` and commit.
4. Presigned snapshot URLs need an R2 API token with Object Read & Write on `tumpel-sessions-<stage>` only. OpenTofu manages it: `tumpel-r2-<stage>` in `infra/tokens.tf`, minted through the provider alias `bootstrap`, which uses the account's token-minting key `reader-cloudflare-tofu-token` because Cloudflare refuses Account API Tokens Write on a token another token minted, so `tumpel-tofu` cannot hold it. `npm run deploy` decrypts the key in process from dotfiles and passes it as `TF_VAR_bootstrap_api_token`. The output `worker_secrets` derives the S3 key pair from the token (access key id is the token id, secret is the SHA-256 hex of the token value) and `npm run deploy` puts `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` on the Worker after deploying it. The Worker signs short-lived snapshot upload and download URLs with it; hosts never hold a storage key.

The Worker reads its turn budgets, snapshot delay and deadline, dispatch grant lifetime and transcript chunk size from the `TUMPEL_SETTINGS` var in `wrangler.jsonc`, checked against `ControlPlaneSettings` in `packages/api/models.tsp`.

Commands, for bootstrap only:

- `npm run deploy` applies the infra of the stage, refuses a plan that destroys anything, applies D1 migrations, deploys the Worker with `ACCESS_ISSUER` and `ACCESS_AUD` taken from the tofu outputs and sets the three R2 Worker secrets.
- `npm run deploy:migrate` applies D1 migrations only.
- `npm run proof:e2e` validates a stage after its deploy: it runs the twelve steps of EDD-006 against the stage's Worker and the host `TUMPEL_PROOF_HOST` (default `tumpel-host`) with the release binaries from `cargo build --release -p tumpel` and `npm run supervisor:build`, and loads the provider credential named by `TUMPEL_PROOF_CREDENTIAL` (`dotfiles:<key name>`, default `dotfiles:claude-setup-token-personal`, or `claude-credentials[:<path>]`) in process.
- `npm run proof -- <command>` runs a command with `TUMPEL_PROOF_CLIENT_ID` and `TUMPEL_PROOF_CLIENT_SECRET` read from the stage's tofu outputs. It prints neither value.

Sign a terminal in with `tumpel login --endpoint https://tumpel-control-plane-dev.matthijs-f49.workers.dev`.

The end-to-end proof signs in without a person: `infra/proof.tf` mints the Access service token `tumpel-proof-<stage>` through the provider alias `bootstrap` and lets it through the Access application with a `non_identity` policy. `npm run deploy` sets its client id as the Worker var `ACCESS_PROOF_COMMON_NAME`; the Worker accepts that service token on `/v1/device/approve` and `/v1/device/deny` only, as the owner of the tenant `Tumpel proof`, whose tenant and principal ids derive from the client id and are created on first use. `npm run proof -- tumpel login --endpoint <stage url>` approves its own code with it.
