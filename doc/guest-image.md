# Guest image

`npm run release:fetch -- guest` puts the `tumpel-guest` of the supervisor release that `pins/supervisor.json` names at `.tmp/release-binaries/tumpel-guest`, and `TUMPEL_GUEST_BIN` names another. `npm run guest:image -- <harness> [amd64|arm64]` then builds a read-only ext4 rootfs without root, for `ClaudeCode` from the harness catalog, `Shell` for tests, or `all` for both, for the given architecture, by default the build machine's. It refuses arm64 unless `BUILD_ARM64=true`. It writes `<digest>.ext4`, `<digest>.json` (`GuestImageManifest`) and `<kernelDigest>.vmlinux` to `$TUMPEL_IMAGE_DIR`, by default `~/development/.tmp/tumpel-images`.

The build:

1. Downloads the Firecracker CI Ubuntu 24.04 squashfs and kernel, the Ubuntu `git` and `libcurl3t64-gnutls` packages, the Ubuntu packages listed in `npm-scripts/guest-packages.mjs` (written by `npm run guest:packages -- <arch> <base rootfs squashfs>`, which resolves them against the base), the GitHub CLI `gh`, the Node LTS runtime, `fnm`, `uv` and `rustup-init`, each checked against the digest pinned in `npm-scripts/guest-image.mjs`. It fetches each Ubuntu package from the Ubuntu mirrors in order, then from the Ubuntu snapshot service at the time the resolver recorded for it, and from Launchpad last. The snapshot service keeps the versions the mirrors drop once Ubuntu supersedes them, such as `libc6-dev` and `perl`, which must match the exact `libc6` and `perl-base` of the base rootfs. `npm run guest:sources -- <arch>` checks that a mirror or the snapshot service serves every pinned Ubuntu package. A server error, a network error or a mirror 404 moves to the next source; a 404 from Launchpad, any other error or a digest mismatch stops the build.
2. Unpacks the squashfs with `unsquashfs`, unpacks the packages with `dpkg-deb -x` and `gh` into `/usr/local/bin`, installs the tooling under Preinstalled tooling, running the build machine's own `uv` and `rustup-init` to fetch Python and the Rust toolchain, adds `tumpel-guest`, its systemd unit, `/usr/local/sbin/tumpel-init` and `/etc/tumpel/guest.json` (`GuestHarness`), and runs `npm install` for the linux platform package of the catalog's pinned Claude Code release, whose native `claude` binary is the harness command. It writes `/etc/.updated` and `/var/.updated` with the time `/usr` last changed, so systemd skips `ldconfig`, the journal catalog and `sysusers` at boot. Without them those jobs ran on every boot, ran for about 4 s and held back the guest agent's hello by about 3 s.
3. Packs the tree with `mkfs.ext4 -d` and sets every inode to root with `debugfs`.

In the box, `tumpel-init` mounts the second drive as the overlay upper directory and formats it on first boot. It then pivots into the overlay and starts systemd. `tumpel-guest` listens on vsock port 1024 and announces itself on host port 1025. It keeps one harness process per box and starts it with the turn's provider key in the environment variable `providerKeyName` in `guest.json` names. A turn whose key or model differs from the running process's restarts the harness, continuing the conversation. The key is never written to the guest disk or logged. Before the harness starts, the guest clones the turn's `repository` into the empty harness working directory, `/root/workspace`, at its default branch, as a partial clone with `--filter=blob:none` so git fetches history blobs on demand; git reads `GITHUB_TOKEN` from the environment through a credential helper set in `GIT_CONFIG_*` variables, and `gh` reads it as `GH_TOKEN`. When the turn carries `TUMPEL_GITHUB_TOKENS`, one installation token per account the tenant installed the GitHub App on, the credential helper answers each `github.com/<owner>/` path with that owner's token, and a `gh` wrapper in `/var/lib/tumpel/bin` picks the token of the owner the command names, else of `GH_REPO`, else of the working repository's origin; for an owner without an installation it keeps the session token. A directory that already holds a repository, on a resumed or restored box, is left as it is.

`/etc/gitconfig` keeps git within a small box's memory: it turns off automatic gc and maintenance, packs and indexes packs with one thread, caps the delta window, delta caches and mapped pack windows, and stores files over 64 MiB without delta compression. The mapped pack windows matter: a repack of a 300 MB file with two revisions peaks at 132 MiB with them and 577 MiB without. A `git add` of a file over 64 MiB in the partial clone prints two `fatal:` lines and succeeds, because git 2.43 and later fetch the new blob from the promisor remote before writing it and ignore the failure; the persona notes tell agents not to retry. A fetch resolves one delta at a time and holds that blob's base and result in memory, so it peaks at about twice the largest delta-compressed blob it receives. GitHub refuses files over 100 MiB, so a fetch from GitHub stays under 260 MiB.

Every image, the base included, ships this tooling for root, the user the harness runs as. The harness `PATH` is `/root/.local/share/fnm/aliases/default/bin:/root/.cargo/bin:/root/.local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`, so every command below runs in a non-interactive shell without sourcing a profile. `fnm install` and `fnm default` switch the Node on `PATH`, `uv python install` adds Pythons, and `rustup toolchain install` adds Rust toolchains; each writes to the box's overlay disk, not the image. The base carries Playwright's Chromium headless shell dependencies. Each repository's prebuild installs its Playwright browser. A repository's prebuild adds only what that repository needs on top of this set.

Building an image needs `unzip` on the build machine besides the tools under Host prerequisites. The tooling adds about 1.6 GB to the image tree, the Rust toolchain 653 MB, the Node and Python runtimes about 330 MB and the Ubuntu packages about 630 MB, and grows the base's ext4 from 943 MB to 2,901 MB. Harness layers carry no tooling; they sit over the base. A host downloads the base as that uncompressed ext4, so a host that fetches a new base moves its full size, about 2.9 GB, plus the 28 MB kernel and the harness layer, within `turnImageFetchBudgetSeconds` (900 seconds) for all three together. That needs at least 4 MB/s, about 32 Mbit/s, from the host to the release bucket; a slower host fails the turn `ImageFetchTimedOut`. Firecracker attaches the ext4 as a read-only block device and reads it on demand, so boot reads only the blocks it touches.

## Guest drive

The supervisor release of tumpel/supervisor embeds the guest drive: `tumpel-guest`, its systemd unit, the guest drive's `init` and `base-layout` (`BaseLayout.Version`) in one squashfs. At start the supervisor writes its drive to `<imageCacheDir>/guest/<sha256>.squashfs`, deletes every other file there, and exits `GuestDriveUnwritable`, code 8, when it cannot within 60 seconds.

The guest drive's `init` runs from the base's stub init, with the drive mounted at `/opt/tumpel/guest`. It fails `base-layout` unless the base's `/etc/tumpel/base-layout` holds the drive's `base-layout`, then mounts the stack of EDD-007. It reads the harness mount point from `tumpel.harness=<harness>/<version>` on the kernel command line, needs `/opt/harness`, `/opt/tumpel/guest`, `/run`, `/mnt`, `/rom` and `/overlay` in the base, and enables the unit from a tmpfs at `/run/systemd/system`.

The vsock protocol is length-prefixed JSON: a 4-byte big-endian length, then one `GuestMessage` from the guest or one `GuestTurnStart` from the host, as `supervisor.tsp` defines them.

## Host prerequisites

- `/dev/kvm` readable by the supervisor's user (group `kvm`), and Firecracker v1.18.0 at `firecrackerPath` in `runtime.json` (`SupervisorRuntime`). Firecracker runs unjailed as that user.
- A pool of `boxCapacity` TAP devices owned by that user, made once by `tumpel-supervisor install` (see `test-host.md`). Device `tumpel<k>` is a TAP with host address 172.16.<k>.1/30 and IPv4 masquerade, made by systemd-networkd or, without networkd, by `tumpel-tap-pool.service`, and its guest takes 172.16.<k>.2/30. The supervisor never needs `CAP_NET_ADMIN`. Egress is open to the internet; private and link-local destinations are dropped.
- `unsquashfs`, `mkfs.ext4`, `debugfs`, `e2fsck` and `dpkg-deb` on the machine that builds images.

The host test that runs a Shell box through boot, a turn, a snapshot, resume and a second turn lives in tumpel/supervisor.
