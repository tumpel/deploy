# 007. Connector tokens reach harnesses through a guest-local forwarder

Status: proposed

A connector's access token expires during a long turn. Each of the four catalog harnesses has to send a fresh token on its next MCP request, and the refresh token has to stay in the tenant Durable Object ([RFC: Connectors](../RFC/RFC-TUM-Connectors.md), R5). Three designs deliver the token:

| Option                | Changes and refresh-token location                                                                                                      | Failure and cost                                                                                                                                                                                                                                 |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Guest-local forwarder | One listener in the guest fetches access tokens from the Worker over HTTPS. The refresh token stays sealed in the tenant Durable Object | The guest gains streaming HTTP forwarding. Every harness shares one behaviour                                                                                                                                                                    |
| Native header hooks   | A helper per harness fetches access tokens from the same endpoint. The refresh token stays in the control plane                         | Claude Code refreshes on connect and on rejection. Codex caches helper output until rejection and can replay a POST. OpenCode fixes headers at connection. Pi caches command results. OpenCode and Pi need upstream changes or forced reconnects |
| Native OAuth caches   | The guest seeds each native store, the harness refreshes and reports rotated credentials back                                           | The refresh token enters the VM. Concurrent sessions can spend the same rotating token. Four storage and locking integrations fight central ownership                                                                                            |

Hook evidence: [Claude Code](https://code.claude.com/docs/en/mcp#use-dynamic-headers-for-custom-authentication), [Codex 0.169.0](https://github.com/openai/codex/blob/rust-v0.169.0/codex-rs/rmcp-client/src/http_headers.rs), [OpenCode 1.19.5](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/mcp/index.ts), [Pi 1.5.2 runtime](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/extensions/mcp/runtime.ts) and [command cache](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/core/resolve-config-value.ts).

The guest runs one forwarder for every connector, static and OAuth. Each harness gets a fixed loopback URL per connector in plain HTTP MCP config. The forwarder adds the upstream credential to each request and fetches a new access token before the old one expires.

The native hooks give no shared proactive-refresh path at these pins, and native caches put the refresh token in the box. The forwarder costs a streaming HTTP listener in the guest, which tumpel/supervisor ships. It buys one refresh path for all four harnesses, and the harness config holds no secret. The agent can still read an access token from guest memory, because the VM is the trust boundary.
